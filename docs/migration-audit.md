# Migrating public Python sqlc projects

On 22 November 2026 we generated Python for 100 of 104 sqlc entries from 81 of 85 downstream projects. Those 100 entries contained 2,401 query declarations, counting shared examples and forks. We generated each with SQLAlchemy and its engine’s native backend, both sync and async. Each combination is one profile. [Pinned project inventory](audits/python-sqlc-projects.tsv)

| Effort per downstream entry | Entries | What changed |
| --- | ---: | --- |
| Original SQL, ordinary backend options | 69 | Selected a backend and execution mode. This includes reproducing one Nix-generated configuration. |
| Original SQL, additional configuration or a converter | 3 | Declared a pgvector type override, selected the migration that defines the queried schema, or converted a driver's bit mask. |
| Changed or recovered SQL | 28 | Added casts or named parameters, repaired SQL, or recovered a schema or query declarations from the project. |
| Missing input | 4 | The referenced queries or authoritative schema were unavailable. |

We inspected 136 public checkouts. We searched GitHub for generated-file headers, plugin names and URLs, configuration options, repository descriptions and README mentions. Seven repositories contained generator fixtures or copies of upstream tests. The downstream count includes applications, libraries, templates and tutorials. The search could miss public projects and excludes private repositories. The table counts configuration entries that generated Python. The database and application checks below show what ran.

The follow-up audit measures caller changes and repeats the same upstream tests with both generators. Its expanded search screened 147 candidates. [Application migration results by engine](application-migration-audit.md)

## What changes at a call site

The official generator puts queries on a `Querier` bound to a connection. This plugin takes the connection as a function argument. Supply named arguments or the configured `Params` record, consume a `:many` result as a list or use its `stream_` context manager, and read record fields by name. The application still owns the transaction. The community generator already emits functions, so a port can often keep its call structure. [Official generator](https://github.com/sqlc-dev/sqlc-gen-python/tree/53fa0b2e3d10c4201f7a5a344d00a560330da3bb) · [Community generator and driver support](https://github.com/rayakame/sqlc-gen-better-python/blob/dab99a8c1418c9a13c9621998029d50bc2aed6c7/docs/content/docs/reference/feature-support.md)

We built both reference plugins and ran them through sqlc on Nixbot’s approvals, Riverqueue’s jobs and Mosaic’s authors. The official generator supports `:one`, `:many`, `:exec`, `:execrows` and `:execresult`. The community generator adds last-insert IDs on MySQL and SQLite and bulk COPY on PostgreSQL. This plugin supports the five official commands, MySQL last-insert IDs, PostgreSQL batch commands and counted `:copyfrom` on all three engines. Read-only `:many` queries also have a streaming function. [Official query command implementation](https://github.com/sqlc-dev/sqlc-gen-python/blob/53fa0b2e3d10c4201f7a5a344d00a560330da3bb/internal/gen.go#L890-L966) · [Supported backends and query commands](../README.md)

Three choices affected callers. To keep asyncpg, pass a SQLAlchemy async connection. If SQLite stores a timestamp as text, convert it on reads and writes. For code that depends on a specific record library, choose dataclasses or Pydantic for the entry. [Community converter interface](https://github.com/rayakame/sqlc-gen-better-python/blob/dab99a8c1418c9a13c9621998029d50bc2aed6c7/docs/content/docs/guide/converters.md)

## What counted bulk inserts require

With SQLAlchemy on asyncpg we issue one insert per input row because the driver’s bulk call supplies no row count. In a 10,000-row test a trigger skipped 200 rows. The generated loop returned 9,800.

We tried two faster paths. A multi-row insert reduced statement-trigger firings from 10,000 to 20. Pipelining inserts with `RETURNING 1` kept the count and trigger behavior on a table, but PostgreSQL rejected it on a view whose insert rule accepts the original SQL. The acceptance suite covers that view and rollback to a savepoint after a failed batch. [Runtime scenarios](../tests/python/suite/test_runtime.py)

## Verification and replay

Pinned sqlc v1.31.1 ran the release WASM on every successful entry. Its output matched the native generator byte for byte on 400 downstream packages and 252 fixture packages. All 652 passed Ruff, mypy strict and pyright strict, as did the two converter packages. Compared with the first audit, Python files changed in 76 downstream packages across 19 entries and in 44 fixture packages. [sqlc revision](https://github.com/sqlc-dev/sqlc/tree/a95e91d70ad9e1181253c333a1cfdd75ae4b95a5) · [Repository checks](testing.md)

Additional PostgreSQL driver checks exercised the repaired predicates, a numeric union and a nullable expression read through two CTEs. Both arms of the union returned `Decimal` for present values. A two-dimensional JSON array accepted JSON lists as leaves and rejected a scalar in place of a required subarray. The same cases ran on raw psycopg in both modes, SQLAlchemy on psycopg in both modes, and SQLAlchemy on asyncpg. A separate psycopg check used a registered composite loader that returns one Python list per element. Strict caller checks also accepted existing `list[UUID]` variables and lists containing both UUIDs and `None`.

Of 368 downstream PostgreSQL packages, 316 had distinct combinations of schema, queries, options and generated Python. We counted a read once it returned a row and compared each synchronous result with the original SQL. Four GPX DB profiles could not run on the original schema.

| PostgreSQL sweep | Packages that ran | Functions exercised | Synchronous calls compared with SQL |
| --- | ---: | ---: | ---: |
| Initial run | 312 | 6,610 / 9,004 | 311,403 |
| Rerun of packages whose Python changed | 76 | 4,057 / 5,584 | 194,233 |
| Final count, including earlier runs for identical Python | 312 | 6,593 / 9,004 | 311,657 |

We installed pgvector, PostGIS, RUM and pg_idkit where the project required them. Fixture repairs included a missing sequence, a misspelled foreign key and two migrations that provision roles. We bounded the demo’s `generate_series` range to four and drew geometry, order status and payment status arguments from their declared domains.

We reran the 76 changed packages against their project schemas. Two Attenborough profiles hit the five-second statement timeout when run in parallel. Both passed separately with the same timeout and inputs bounded as before. The other 240 distinct packages generated byte-identical Python, so we retained their earlier results. Some functions never returned a row or received arguments the database would accept.

The remaining four PostgreSQL profiles belong to GPX DB. Its schema creates a foreign key before its target table exists, joins a UUID foreign key to a nonunique text column, and indexes a missing column. Its checked-in files give conflicting evidence about the intended key type. Two separate patches make both ends text or both ends UUID. Each passed strict tooling and ran on all four profiles. The runtime totals above use the original schema. [GPX DB schema](https://github.com/Maxxxxxx-x/gpx-db/blob/e86cfdc3abe9bd69e169ce8215ac13f7b377a08d/src/db/schema/000001-init-schema.sql)

All six SQLite entries and both MySQL entries ran application-specific scenarios on their four profiles. Both MySQL entries also ran against MariaDB 11.4, giving 40 successful profile/database runs. The scenarios covered CRUD, iteration, nullable filters, computed statistics, datetime conversion and missing records, according to the entry. All 40 scenarios were repeated on the final packages. Four projects also reran selected application code against their migrated queries. Coverage of web services and deployed applications is outside these figures.

The local archive `target/migration-audit/python-sqlc-projection-replay.tar.gz` contains the configurations, SQL and caller patches, converters and results. Its README explains how to run `replay.py` on a fresh checkout. The script fetches the pinned revision, applies the SQL changes and generates all four packages. `projection-replay.tsv` compares native and WASM output. `final-postgres.tsv` identifies which database runs we repeated. The project revisions and counts are also in the checked-in inventory.

The audit found one upstream PostgreSQL fixture that compares a single parameter with an integer ID and a `varchar` name. PostgreSQL rejects `FindByIDAndName` with SQLSTATE 42883. An early generation check also rejected the valid `integer`/`bigint` case. We removed that check. All six profiles now generate, so the valid neighboring query is usable. Executing the incompatible comparison still requires fixing the original SQL. [Captured request](../tests/sqlc/endtoend/params_placeholder_in_left_expr/postgresql/request.json)

In the repository checks for this run, 2,040 generated packages passed strict Python tooling. The PostgreSQL sweep exercised 2,774 of 3,027 functions across 928 APIs, with 124,908 calls matching the original SQL. Driver probes found zero mismatches. The runtime tests and probes also passed on Python 3.15. Each intended check caught its planted bug, 34 in all. The sqlc capture reproduced 603 distinct requests and the WASM wrote the expected example files. [Repository test layers](testing.md)

In three PostgreSQL cases, a nullable column and a required one produced identical plugin requests. Applications that require a value from a computed view, an inheritance parent or a table created with `AS` need a guarantee in the SQL. Our capture test reads both schemas against PostgreSQL, so it can detect an upstream fix. On SQLite, use `STRICT` tables or validate what other writers can store. [Driver and schema limitations](../README.md#known-limitations)

## Populated queries and application tests

Four follow-up GitHub code searches returned 54 distinct repositories, all already in the inventory. We regenerated five pinned projects with the WASM plugin. For three PostgreSQL projects we supplied related records, passed the IDs through the generated functions and checked the returned values. Each scenario ran on psycopg and SQLAlchemy, sync and async. The table shows counts **per profile**. A function that returns three rows counts once under functions and three times under rows. Counts and other scalar query results count as one row. The row totals include streaming reads.

| --- | ---: | ---: | ---: | ---: | ---: |
| Smart Credit Office, main repository | 18 | 127 | 117 | 104 | 104 |
| Personal Agent | 27–34 | 110 | 110 | 105 | 114 |
| INF326 message service | 29–31 | 38 | 38 | 37 | 81 |

Across the four profiles the scenarios returned **1,196 rows**. The earlier sweep exercised 309 function/profile combinations for these entries. The populated scenarios completed 1,060, so at least **751** of those successful combinations were new. These figures overlap the earlier PostgreSQL totals.

- **Smart Credit Office** linked 18 tables, from users and loan applications to decisions, audit events and jobs. The tests checked exact JSON payloads, filtered reads, deletion and a worker claiming a job once. Updating or deleting an existing row in any of five immutable history tables raised the expected PostgreSQL error `23514`. Those ten functions account for the difference between calls and successful completions. [Upstream queries](https://github.com/GoshaMak/smart-credit-office/blob/2aa32d294ee698e4438c5259c8f226382dcb9532/backend/db/queries/repository.sql)
- **Personal Agent** indexed two chunks with different 1,024-dimensional embeddings. The full-text search returned the chunk containing the word, and pgvector returned the chunks in the expected order with cosine similarity scores of 1 and 0. The same scenario exercised a job lease and retry, a conversation that cites the document, and an update that archives an older memory. [Upstream queries](https://github.com/Coosis/personal-agent/blob/044fdba88c25f13bee93d86a812efe074934e1ad/sql/query.sql)
- **INF326** exposed a downstream timestamp bug. With the client in Amsterdam and PostgreSQL in UTC, passing midnight on 5 January to an update or soft delete stored 23:00 on 4 January through asyncpg. PostgreSQL reported a `timestamptz` parameter for `COALESCE($n, NOW())` even though the target column was `timestamp`. Using `LOCALTIMESTAMP` in the two expressions gave the parameter the column's type. All four profiles then preserved midnight and returned the expected IDs for search, pagination, soft deletion and restoration. [Upstream queries](https://github.com/KroderDev/INF326-tarea-2/blob/0b26fe815af5b3187127fdb39f8b4ecfaee4e285/service/db/queries/messages.sql) · [PostgreSQL current date and time](https://www.postgresql.org/docs/18/functions-datetime.html#FUNCTIONS-DATETIME-CURRENT)
