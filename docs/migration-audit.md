# Migrating public Python sqlc projects

On 22 November 2026, 100 of 104 downstream sqlc entries generated Python on all four applicable profiles. These entries came from 81 of 85 projects and contained 2,401 query declarations, counting shared examples and forks. A profile means SQLAlchemy or the engine's native backend, each in synchronous and asynchronous mode. [Pinned project inventory](audits/python-sqlc-projects.tsv)

| Effort per downstream entry | Entries | What changed |
| --- | ---: | --- |
| Original SQL, ordinary backend options | 70 | Selected a backend and execution mode. This includes reproducing one Nix-generated configuration. |
| Original SQL, additional configuration or a converter | 3 | Declared a pgvector type override, selected the migration that defines the queried schema, or converted a driver's bit mask. |
| Changed or recovered SQL | 27 | Added casts or named parameters, repaired SQL, or recovered a schema or query declarations from the project. |
| Missing input | 4 | The referenced queries or authoritative schema were unavailable. |

The inventory covers 136 public checkouts. GitHub searches used the generated-file header, plugin names and URLs, configuration options, repository descriptions and READMEs. Seven repositories contain generator fixtures or copies of upstream tests. The downstream population includes applications, libraries, templates and tutorials. Private repositories, unpublished inputs and projects absent from the search results are outside these totals. A successful generation says that the query interface builds. The database and application checks below give the evidence for its behavior.

## What changes at a call site

The official generator puts queries on a `Querier` bound to a connection. This plugin takes the connection as a function argument. Supply named arguments or the configured `Params` record, consume a `:many` result as a list or use its `stream_` context manager, and read record fields by name. The application still owns the transaction. The community generator already emits functions, so a port can often keep its call structure. [Official generator](https://github.com/sqlc-dev/sqlc-gen-python/tree/53fa0b2e3d10c4201f7a5a344d00a560330da3bb) · [Community generator and driver support](https://github.com/rayakame/sqlc-gen-better-python/blob/dab99a8c1418c9a13c9621998029d50bc2aed6c7/docs/content/docs/reference/feature-support.md)

Both reference plugins were built from source and run through sqlc on Nixbot's approvals, Riverqueue's jobs and Mosaic's authors. The official generator implements `:one`, `:many`, `:exec`, `:execrows` and `:execresult`. The community generator also provides last-insert IDs on MySQL and SQLite and bulk COPY on PostgreSQL. This plugin covers those commands, PostgreSQL batch commands and counted `:copyfrom` on all three engines. Its read-only `:many` queries also generate a streaming function. [Official query command implementation](https://github.com/sqlc-dev/sqlc-gen-python/blob/53fa0b2e3d10c4201f7a5a344d00a560330da3bb/internal/gen.go#L890-L966) · [Supported backends and query commands](../README.md)

Three choices affected application code during migration. A community project using native asyncpg needs a SQLAlchemy async connection to keep that driver. Applications that store SQLite timestamps as text can supply local conversion functions. Code that depends on a particular record library must use the frozen dataclass or Pydantic representation selected for the entry. [Community converter interface](https://github.com/rayakame/sqlc-gen-better-python/blob/dab99a8c1418c9a13c9621998029d50bc2aed6c7/docs/content/docs/guide/converters.md)

## Verification and replay

Pinned sqlc v1.31.1 ran the release WASM on every successful entry. Its output matched the native generator byte for byte on 400 downstream packages and 252 fixture packages. All 652 passed Ruff, mypy strict and pyright strict, as did the two converter packages. [sqlc revision](https://github.com/sqlc-dev/sqlc/tree/a95e91d70ad9e1181253c333a1cfdd75ae4b95a5) · [Repository verification methodology](testing.md)

The 368 downstream PostgreSQL packages included 316 distinct combinations of schema, queries, options and generated Python. On 312 of these, the runtime sweep exercised 6,610 of 9,004 generated functions across profiles. It checked returned rows against their annotations and matched 311,403 synchronous calls against the original SQL run directly. A row-returning function counts as exercised once a call returns a row. The sweep used pgvector, PostGIS, RUM and pg_idkit where projects required them. The fixture notes record deployment adjustments, including a missing sequence, a misspelled foreign key and two migrations that provision database roles. For the demo using `generate_series`, we bounded the generated range to four. For geometry arguments and order and payment statuses, we drew values from their declared domains.

The remaining four PostgreSQL profiles belong to GPX DB. Its schema creates a foreign key before its target table exists, joins a UUID foreign key to a nonunique text column, and indexes a missing column. Its checked-in files give conflicting evidence about the intended key type. Two separate patches make both ends text or both ends UUID. Each passed strict tooling and ran on all four profiles. The runtime totals above use the original schema. [GPX DB schema](https://github.com/Maxxxxxx-x/gpx-db/blob/e86cfdc3abe9bd69e169ce8215ac13f7b377a08d/src/db/schema/000001-init-schema.sql)

All six SQLite entries and both MySQL entries ran application-specific scenarios on their four profiles. Both MySQL entries also ran against MariaDB 11.4, giving 40 successful profile/database runs. The scenarios covered CRUD, iteration, nullable filters, computed statistics, datetime conversion and missing records, according to the entry. Four projects also ran selected application code against their migrated queries. Coverage of web services and deployed applications is outside these figures.

The local replay archive under `target/migration-audit/` contains per-entry configurations, SQL and caller patches, converter modules and profile-level results. Its `replay.py` fetches the pinned project into a new checkout, applies the SQL changes and generates all four packages. The archive's README gives the command and required paths. The checked-in inventory retains the revisions and migration counts when the build directory is cleaned.

The repository's own verification passed separately. Its static gate checked 2,043 packages. Its PostgreSQL sweep checked 933 APIs and matched 125,049 calls against the original SQL. All 32 planted bugs were caught by their intended checks. The capture check reproduced 603 distinct requests and exercised the release WASM through sqlc. [Repository test layers](testing.md)
