# Generated Python: the output specification

This is the normative definition of what the plugin emits: for PostgreSQL
through SQLAlchemy Core 2.x or psycopg 3, and for SQLite through SQLAlchemy or
`sqlite3` and `aiosqlite`, each sync and async. "MUST" is a requirement on the
generator. A rule that is not here is not a promise.

The acceptance fixture is `tests/schemas/src/invoicing/` on PostgreSQL. Its
byte-exact output is the golden cases `tests/cases/invoicing_sqlalchemy/` and
`tests/cases/invoicing_psycopg/`, proven by `cargo xtask verify` (see
[Proof](#proof)). `tests/schemas/src/ledger/` is SQLite's, as
`tests/cases/ledger_sqlalchemy/` and `tests/cases/ledger_sqlite3/`. When this
document and those files disagree, that is a bug in one of them.

Every rule cites the source of truth it rests on, using the ranking in
`CLAUDE.md`:

| Tag | Source |
|---|---|
| **[1]** | the sqlc plugin contract (`protos/sqlc.proto`, sqlc's runner) |
| **[2]** | what the pinned sqlc (`tests/corpus/SOURCE.toml`) puts in the request |
| **[3]** | what PostgreSQL and the drivers return at runtime (the versions recorded at the top of `docs/typemap.md`) |
| **[4]** | sqlc-gen-go and sqlc's inflection rules |
| **[5]** | pyright strict, `mypy --strict`, ruff `ALL` (the [lint contract](#lint-contract)), all targeting Python 3.10 |
| **[D]** | a decision recorded in `CLAUDE.md` or below, with its reason |

## 1. Files

1. Each codegen output MUST consist of exactly these files, all in `out`:
   - `__init__.py`, holding only the header, and on a backend without errors
     of its own for `:one` (psycopg, `sqlite3`), the two it raises (§6,
     "Functions", rule 3);
   - `models.py`;
   - one query module per query file, named after the file's stem
     (`invoices.sql` becomes `invoices.py`).

   *[4]: Go emits one file per query file. [D]: the generated package owns
   `out` the way Go's package does. `__init__.py` makes it a regular package, so
   relative imports and mypy work without configuration and ruff INP001 holds.
   There is no `py.typed`: the package lives inside the application's own
   distribution, and PEP 561 reads the marker only at that distribution's
   root, which is the application's to write (sqlc never deletes a file it
   did not write). The static gate imports every package as installed, with
   that marker.*
2. A query file whose stem is `models` or `__init__` in any case, or is not a
   lowercase Python identifier (`Invoices.sql`, `query.v2.sql`), MUST be an
   error. *[1]: sqlc would silently overwrite the other file, and on a
   case-insensitive file system (macOS, Windows) `Models.py` is `models.py`.
   [5]: ruff N999.* So MUST an `out` whose last part is not one
   (`out: app/my-db`): the package's own modules import each other
   relatively, so it is only usable imported by that name. *[5]*
3. Every module MUST start with this header, and nothing else is a comment:

   ```python
   # Code generated by sqlc-gen-python. DO NOT EDIT.
   # versions:
   #   sqlc-gen-python v0.1.0
   #   sqlc v1.31.1
   ```

   The sqlc line MUST be left out when `omit_sqlc_version` is set, or when the
   request has no `sqlc_version`. There is no `# source:` line: ruff ERA001
   reads it as commented-out code, and the module name already says it. *[4], [5]*
4. Output MUST be exactly what ruff's formatter produces with default options,
   and imports MUST be sorted as ruff's isort (I001) sorts them. *[5]*

## 2. Imports

1. A module MUST import exactly what it uses, from this fixed vocabulary:

   | Use | Import |
   |---|---|
   | dataclasses, enums | `import dataclasses`, `import enum` |
   | dates and times | `import datetime as dt` |
   | `Decimal`, `UUID` | `from decimal import Decimal`, `from uuid import UUID` |
   | network types | `from ipaddress import IPv4Address, IPv6Address, ...` |
   | `Iterable`, `Sequence` | `from collections.abc import ...` |
   | `Any`, `Final` | `from typing import ...` |
   | SQLAlchemy | `import sqlalchemy`, `from sqlalchemy.dialects import postgresql`, `from sqlalchemy.ext.asyncio import AsyncConnection` |
   | psycopg | `import psycopg`, `from psycopg.rows import tuple_row`, `from psycopg.types.json import Json, Jsonb` |
   | SQLite | `import sqlite3`, `import aiosqlite` |
   | the models, and the errors of `:one` | `from . import MultipleRowsError, NoRowError, models` |

   *[D]: a column named `datetime`, `uuid` or `decimal` would shadow a module
   imported under that name. mypy then misreads the dataclass annotations that
   follow it. That is a probed bug, not a style point. PascalCase names cannot
   collide with snake_case fields, and `dt` is ruff's ICN001 default alias.*
2. Query modules MUST reach models through `from . import models` and
   `models.X`. There is no `package` option. *[D]: relative imports resolve
   wherever `out` lives.*

## 3. Names

| Thing | Rule | Example | Source |
|---|---|---|---|
| model class | sqlc inflection: singular, PascalCase, schema prefix outside the default schema | `media` → `Medium`, `billing.payments` → `BillingPayment` | [4]: `src/inflection.rs` ports sqlc's `internal/inflection`, quirks included (`leaves` → `Leafe`), and is held to `tests/corpus/inflection.tsv`, captured from sqlc's own code |
| enum class | PascalCase, schema prefix outside the default schema, never singularised | `billing.payment_method` → `BillingPaymentMethod` | [4] |
| enum member | Go's `EnumReplace` (`-`, `/`, `:` and `_` become `_`; other characters that are not ASCII letters or digits are dropped), then upper-cased. | `direct-debit` → `DIRECT_DEBIT` | [4], PEP 8 |
| function | snake_case of the query name | `GetInvoiceWithCustomer` → `get_invoice_with_customer` | PEP 8 |
| SQL constant | `_` + UPPER_SNAKE of the query name | `_GET_INVOICE_WITH_CUSTOMER` | [D]: private, like Go's unexported constants |
| result class | `<Query>Row` | `GetInvoiceTotalsRow` | [4] |
| `:copyfrom` input class | `<Query>Params` | `CreateLineItemsParams` | [4] |
| field / parameter | snake_case of the column or parameter name. A name sqlc leaves empty is `column_<position>`, counting from 1. | | [4] (`columnName`, which Go's `Params` struct fields follow too); [D]: Go names a lone unnamed parameter `dollar_<N>`, but one rule serves any number of parameters |
| repeated name | Repeats in one result or parameter list get `_2`, `_3`, and so on, in order. | `issued_on`, `issued_on_2` | [4] (`columnsToStruct`) |
| embed field | snake_case of the embedded model's class name | `invoice: models.Invoice` | [4] |

1. A field or parameter whose name is a Python keyword, a name a generated
   module imports (§2: `dataclasses`, `dt`, `enum`, `models`, `postgresql`,
   `sqlalchemy`), or one of the builtins and locals the generated code reads
   (`bool`, `bytes`, `classmethod`, `conn`, `cur`, `float`, `from_row`, `int`,
   `list`, `object`, `row`, `rows`, `str`, `value`) MUST get a trailing
   `_`. In a class body, a field `str` would make every later `str` annotation
   mean the field, and a field `classmethod` the decorator of `from_row`. The
   renamed name is also the bind name (`:from_`), so no mapping is needed.
   *PEP 8; [5]*
2. A column `id` stays a parameter `id`. *[D]: renaming it would put `id_` into
   every call site. The parameter is keyword-only, and the body never calls
   `id()`.* A function, which is module-level, MUST also take the trailing `_`
   when its name is a builtin's: query `Any` is `any_`, and its constant
   `_ANY_`. *[5]: ruff A001.*
3. These MUST be errors, never silent renames:
   - two classes with one name (for example, table `invoice_status` and enum
     `invoice_status`), or a class with the name of an import (§2), such as
     table `sequences` (`Sequence`), which would change what every annotation
     of that name means;
   - two queries of one file that map to the same function;
   - two enum labels that map to the same member;
   - two columns of one table that map to the same field (`user_id` and
     `userId`, or `from` and `from_`);
   - two parameters that map to the same name when the user chose either
     (`sqlc.arg`, `@name`): `"userId" = $1 AND uid = @user_id` would otherwise
     bind the user's `user_id` to `$1`, with the same type, so a swap would
     type-check. Names that are both sqlc's are numbered (rule above);
   - a parameter sqlc named after an expression rather than a name: one the
     user chose (`@name`) whose name, before snake-casing, is no PostgreSQL
     identifier, or starts with `pg_catalog`. `@` is a prefix operator, so
     an operator that binds tighter takes the expression with it, and sqlc
     names the parameter after all of it: `@day::date AT TIME ZONE
     'Europe/Amsterdam'` is `@(timezone(...))`, named
     `pg_catalogtimezoneEurope/Amsterdamdaydate`, and replaced whole with
     `$1`, time zone and all (with `'UTC'` the name is an identifier, but
     still starts `pg_catalog`); `@x + 1` is named `+x`. Write
     `sqlc.arg('day')::date AT TIME ZONE ...`, or parenthesise `(@day::date)`.
     *[2]: probed. Other casts before `AT TIME ZONE`, and `%`, `^` or
     `COLLATE` after `@x`, make sqlc fail itself;*
   - a class, field, parameter, member or module name that is not a public
     ASCII identifier: empty (`=`), starting with a digit (`1st`), starting
     with `_`, which `enum` reserves (`_x_`) or mangles (`__x`), and pyright
     and ruff treat as private (`_1ST`), or not ASCII (`größe`). *Probed:
     pyright strict reports `Rank._1ST` as `reportPrivateUsage` and ruff as
     SLF001, so Go's `_` prefix for a leading digit is not usable from
     application code. [5]: ruff PLC2401. Python NFKC-normalises identifiers,
     so the columns `ﬁle` (a ligature) and `file` would be one keyword
     argument, and the module would not import.*

## 4. Models (`models.py`)

1. Enums come first, sorted by class name, then one dataclass per table, sorted
   by class name. *[D]: deterministic output.*
2. Every record (model, `Row`, `Params`) MUST be declared
   `@dataclasses.dataclass(frozen=True, slots=True, kw_only=True)` with no
   defaults. *[D]: rows are values. Frozen rows cannot be mutated; slots catch
   misspelt attributes; keyword-only construction cannot depend on field order;
   with no defaults, an omitted value is a type error, never a NULL. Proven by
   `usage.py`.*
3. Fields MUST follow the table's column order, with the type given by
   [the type map](#5-types).
4. Every result record (model and `Row`) MUST have a `from_row` classmethod
   that builds it from a row by position:

   ```python
   @classmethod
   def from_row(cls, row: Sequence[Any]) -> "Invoice":
       return cls(id=row[0], ..., status=InvoiceStatus(row[3]), ...)
   ```

   The value expression for field *i* MUST be:
   - `row[i]`, by default;
   - `X(row[i])` for an enum, and `bool(row[i])` for a SQLite `BOOLEAN`
     (§5, "SQLite");
   - `[X(v) for v in row[i]]` for a one-dimensional enum array, or
     `X.from_array(row[i])` on psycopg (§5, "Enums", rule 2);
   - for a nullable enum or enum array, the same wrapped as
     `None if row[i] is None else ...`;
   - `models.M.from_row(row[a:b])` for an embed, where `a:b` covers the embedded
     table's columns.

   *[3]: both drivers return enums as `str`. [D]: matching by position survives
   duplicate column names, and one builder per type replaces the four to six
   inline copies a query module would otherwise repeat. `Sequence[Any]` is the
   honest type of a driver row; the runtime layer checks every value that
   crosses it.*
5. Comments become docstrings, and nothing else does. A table comment becomes
   the class docstring, an enum comment the enum's docstring, a column comment
   an attribute docstring directly under its field, and a query's `comments`
   the function's docstring. sqlc prefixes each query comment line with one
   space, which MUST be stripped. A multi-line docstring MUST indent its
   continuation lines to the docstring's own indentation and put the closing
   quotes on their own line. *[2], [5] (D209)*

## 5. Types

### Type map

This is PostgreSQL's; SQLite's follows. The annotation follows what the
drivers return, not what the old plugins assumed. psycopg as a backend returns
what it returns under SQLAlchemy, which hands its values through untouched. *[3]: every row was observed through SQLAlchemy `text()` on psycopg
(sync and async) and asyncpg; see the evidence column. This is enforced:
`tests/schemas/src/pgtypes` has a column of every mapped type and an array
column of every type whose arrays are allowed (a Rust spec fails otherwise),
and `tests/py/typemap.py` reads every one back through all three drivers, at
its edges.*

| PostgreSQL (`schema.name` with `pg_catalog.` stripped) | Annotation | Evidence and notes |
|---|---|---|
| `bool` | `bool` | |
| `int2`, `int4`, `int8`, `serial*`, `oid` | `int` | A bare `int` is not this type: see rule 2. |
| `float4`, `float8` | `float` | |
| `numeric`, `decimal` | `Decimal` | Scale survives (`'2.500'` stays `2.500`); `NaN` is a `Decimal`. |
| `money` | `str` | Both drivers return a locale-formatted string (`'$12.34'`). It is never `Decimal`. |
| `text`, `varchar`, `bpchar`, `name`, `citext` | `str` | `char(n)` comes back space-padded (`'EU '`). An array of `citext` is an error: an extension type's OID differs per database, so psycopg has no loader for its array and returns the text `'{x}'`, while asyncpg returns a list. |
| `bytea` | `bytes` | NUL and all 256 byte values round-trip. |
| `uuid` | `UUID` | asyncpg returns a `UUID` subclass. |
| `date`, `time`, `timetz`, `timestamp`, `timestamptz`, `interval` | `dt.date`, `dt.time`, `dt.time`, `dt.datetime`, `dt.datetime`, `dt.timedelta` | `timestamptz` comes back timezone-aware: in the session's `TimeZone` on psycopg, in UTC on asyncpg. `'infinity'` and `'-infinity'` raise in psycopg, and asyncpg returns them as the naive `datetime.max` and `datetime.min` (`date.max` and `date.min` for `date`). See [Known limitations](#known-limitations) for what the drivers do with the `datetime` they are given. |
| `json`, `jsonb` | `object` | Both drivers decode (asyncpg through SQLAlchemy's codec). The decoder is configurable (`json_deserializer`), so `object` is the only annotation that is true under every configuration. A recursive `JsonValue` alias was tried by two teams and failed: `get_type_hints` raises `NameError` across modules on 3.14, pydantic hits `RecursionError` on 3.10, and the checkers disagree on `TypeAliasType`. |
| `inet` | `IPv4Address \| IPv6Address \| IPv4Interface \| IPv6Interface` | An address with a prefix comes back as an `Interface`. |
| `cidr` | `IPv4Network \| IPv6Network` | |
| `macaddr`, `macaddr8`, `xml`, `tsvector` | `str` | An array of `tsvector` is an error: asyncpg decodes `ARRAY[''::tsvector]` as a corrupt item, and hangs on an array of it and another item. |
| a catalog enum | `models.X` (`X` inside `models.py`) | coerced by `from_row` (§4, rule 4) |
| `T[]`, `T[][]` | `list[T]`, `list[list[T]]` | `is_array` / `array_dims` from sqlc [2]. psycopg rejects a tuple parameter, so parameters are `list` too. |

1. Any other type MUST be an error naming the column or parameter: ranges,
   geometry, `bit`, `varbit`, `"char"`, `int2vector`, composite types, domains, and
   arrays of `citext`, of `tsvector` or of multi-dimensional enums, and
   `json`/`jsonb` array parameters (each backend binds only a scalar one,
   §6). The drivers disagree on these
   (for example `Range` versus `asyncpg.types.Range`, or `str` versus `bytes`),
   or nobody has probed them. A type is added only together with driver
   evidence. *[3]; CLAUDE.md: never paper over an unknown with `Any`.*
   A domain (`CREATE DOMAIN amount AS numeric(12, 2) CHECK (VALUE >= 0)`)
   arrives as its bare name, never its base type *[2]*, so it is as unknown as
   an extension's type; the error says to declare the column with the base
   type and the domain's `CHECK` as a column constraint instead.
2. A column whose type sqlc could not infer MUST be an error that asks for a
   cast, as `coalesce(<expr>, <default>)::<type>` where the value can be NULL.
   That is an empty type, `any`, and two that look like types but are
   guesses: *[2], probed against sqlc 1.31.1's static analyser*
   - a bare `int` (no schema), which sqlc reports for every arithmetic
     expression, whatever PostgreSQL computes: `quantity * unit_price` on
     `numeric` columns, `unit_price / 1.21`, `d + 1` on a `date`. A column or
     cast of `int` arrives as `pg_catalog.int4`;
   - any column sqlc marks `is_func_call`: it reports the return type of an
     overload it guesses, so `abs(numeric)` and `sum(numeric) OVER ()` arrive
     as `bigint`, `avg(numeric)` as `double precision`, `length(text)` as
     `double precision` and `date_trunc('month', timestamptz)` as `interval`.
     That includes `count(*)`, whose guess is right, because nothing in the
     request tells it apart: write `count(*)::bigint`;
   - a column or parameter whose type is spelled with SQL's standard name:
     `smallint`, `bigint`, `real`, `double precision`, `numeric`, `boolean`,
     `character`, `character varying`, `interval`, and `time` or `timestamp`
     `with` or `without time zone`. sqlc writes a declared or cast type as
     PostgreSQL's own name (`pg_catalog.int8`, `pg_catalog.numeric`,
     `timestamptz`), and these only for a type it read off the signature of
     the overload it guessed, the first it lists with that many arguments.
     So they are a function call read through a view, a CTE or a subquery,
     which loses `is_func_call` (`sum(amount)` on a `numeric` column is a
     `bigint`, and returns `Decimal`), and a parameter passed to a function
     (`abs(@x)` is a `bigint`, `date_trunc('month', @d)` an `interval`). A
     view's column is a model's field, so the cast goes in the view.
     `integer` is not among them: sqlc types LIMIT and OFFSET with it;
   - a `coalesce(x, ...)`, which sqlc reports as the column `x` itself (its
     table, `original_name` and type) but NOT NULL. A NOT NULL result column
     read from a catalog column that admits NULL can only be that, and its
     type is a guess: `coalesce(qty, 1.5)` on an `int` column is annotated
     `int` and returns `Decimal`, `coalesce(d, ts)` is a `dt.date` that
     returns a `dt.datetime`. See [Known limitations](#known-limitations) for
     the coalesce this cannot see.

   A cast is the fix because sqlc reports its type as written. It also
   reports every cast NOT NULL, even of a nullable value, so a bare
   `max(x)::date` would be annotated `dt.date` and return `None` on an empty
   table; hence `coalesce`. See [Known limitations](#known-limitations).

   This rule assumes sqlc's static analysis. Its database-backed analysis (a
   `database` block, unless `analyzer: {database: false}`) reports the types
   PostgreSQL resolves, spelled with SQL's standard names, which nothing in
   the request tells apart from static analysis's guesses: a query that
   compares a `bigint` column with a parameter, or casts a value to
   `numeric`, is then an error. Keep `analyzer: {database: false}` for this
   plugin. *[2]: `format_type` names, probed in the corpus's managed-db
   requests.*
3. Parameter types arrive spelled `{schema: "", name: "billing.payment_method"}`
   or `pg_catalog.int4`, while result columns arrive as
   `{schema: "billing", name: "payment_method"}`. The generator MUST normalise
   both to `schema.name` before the lookup. *[2]*

### SQLite

`sqlite3` and `aiosqlite` return one Python type per storage class, and a
column's declared type decides the class a value written to it is stored as
(its affinity). So the annotation is what generated code, which binds that
type, reads back. *[3]*

| Declared (any case, sqlc's spelling) | Annotation | Notes |
|---|---|---|
| `INTEGER`, `INT`, `TINYINT`, `SMALLINT`, `MEDIUMINT`, `BIGINT`, `UNSIGNEDBIGINT`, `INT2`, `INT8` | `int` | |
| `REAL`, `DOUBLE`, `DOUBLEPRECISION`, `FLOAT` | `float` | |
| `TEXT`, `CLOB`, and `CHARACTER…`, `VARCHAR…`, `NCHAR…`, `NVARCHAR…` | `str` | |
| `BLOB` | `bytes` | |
| `BOOLEAN`, `BOOL` | `bool` | Stored as `0` or `1`; `from_row` converts with `bool(...)`. |
| `DATE`, `DATETIME`, `TIMESTAMP`, `JSON`, `JSONB` | `str` | SQLite has no date or JSON type: the text written is the text read. |

1. `NUMERIC` and `DECIMAL` MUST be an error: their affinity stores `12.50` as
   the float `12.5`. Store money as `INTEGER` cents, or as `TEXT`. So MUST
   `any` or no type, sqlc's report of an expression it could not type (add a
   `CAST(<expr> AS <type>)`), and an array, which SQLite does not have.
2. `sqlc.slice` is not supported yet on SQLite, and MUST be an error.

### Nullability

1. A column or parameter is `T | None` exactly when sqlc reports
   `not_null: false`. That includes surprises such as `as_of` in
   `invoices.due_on < @as_of`, and both `issued_on` parameters. It MUST NOT be
   re-inferred. *[2]*
2. A JSON column is annotated `object | None` when nullable, so the rule stays
   uniform even though `object` already admits `None`.
3. Array elements are never `| None`: `text[] NOT NULL` is `list[str]`. *[4]:
   Go does the same. See [Known limitations](#known-limitations).*

### Enums

1. Each enum MUST be emitted as follows:

   ```python
   class InvoiceStatus(str, enum.Enum):
       """Lifecycle of an invoice. Only drafts may be deleted."""

       DRAFT = "draft"
       ...

       def __str__(self) -> str:
           return str.__str__(self)
   ```

   *[3]: both drivers bind a `str` mixin member as its label, including inside
   arrays, so parameters need no SQLAlchemy type. [D]: without `__str__`,
   `str(member)` and `f"{member}"` differ between Python 3.10 and 3.12, which is
   a silent change in rendered invoices. Planted bug "enum str() differs across
   Python versions". `enum.StrEnum` needs 3.11.*
2. On psycopg, an enum some result reads an array of MUST also have:

   ```python
       @classmethod
       def from_array(cls, text: str) -> "list[BillingPaymentMethod]":
           """The members of an array of this enum, as PostgreSQL writes one: `{a,b}`."""
           return [cls(label) for label in text[1:-1].split(",") if label]
   ```

   *[3]: psycopg knows no type the schema declares, so it returns an array of
   one as the array's text (`'{card,direct-debit}'`). PostgreSQL quotes an
   element only when it is empty, `NULL`, or holds whitespace, a quote, a
   backslash, a brace or a comma, so* such a label MUST be an error on
   psycopg; with none, the text is the labels between braces, split by
   commas. A `NULL` element or a non-default lower bound (`[0:1]={…}`) is no
   label, and raises.

## 6. Query modules

Each query becomes three things, in sqlc's order: its statement constant,
`_<NAME>: Final = ...`, then its `Row` or `Params` class if it has one, then
its function: a coroutine with `async: true`, a blocking function with
`async: false` (§7). *[D]: one flavour per package. A codebase that needs
both generates two packages from the same queries, with two `codegen`
entries; each then has its own model classes.*

### Statement

1. On psycopg and `sqlite3`, the constant MUST be sqlc's `query.text`, as
   written. Both drivers take their database's own placeholders (`$N`, `?`
   and `?N`) and parameters by position, so nothing is rewritten and the
   database runs exactly sqlc's statement. *[1], [2]* `Final` keeps the
   string a literal, which psycopg's `execute` asks for (`LiteralString`).
   *[5]*
2. The SQL string MUST be triple-quoted if and only if the SQL contains a
   newline, and then holds the SQL as
   written, escaping only a backslash, a `"` that would end the string early,
   every character Python's `str.isprintable()` rejects other than a space or
   a tab (control and format characters such as the bidi controls U+202E and
   U+2066 and the zero-width space U+200B, ruff PLE2502 and PLE2515; and
   whitespace an editor breaks a line at or shows as a space, U+2028 and
   U+00A0), whitespace ending a line (`\x20`, ruff W291) and the tabs of a
   line indentation that mixes them with spaces (`\t`, ruff E101). Docstrings
   (§4, rule 5) escape the same, and a tab starting a continuation line,
   which follows the docstring's own indentation, except that they drop
   whitespace ending a line instead of escaping it: a docstring is prose. It
   MUST NOT contain sqlc's `-- name:` line. *[D]: inside `text()`, `:one` would read as a bind; a
   reviewer cannot see an unprintable character, and ruff's unparser escapes
   them in every other string.*

#### On SQLAlchemy

The constant is `sqlalchemy.text("<sql>")`, as SQLAlchemy reads it.

1. **Placeholders.** Every placeholder MUST become `:<python name of its
   parameter>`, and nothing else may: on PostgreSQL each `$N` that
   libpg_query, which sqlc parses with, scans as one; on SQLite each `?` and
   `?N` SQLite's tokenizer reads as one, a `?` numbered one past the largest
   number before it. A number used twice becomes the same name twice. A named
   parameter sqlc left as written MUST be an error: a lone `@` operator
   directly before what starts an identifier (`@amount`, `@"Amount"`), or
   `sqlc.arg`, `sqlc.narg`, `sqlc.slice` or `sqlc.embed`. sqlc 1.31.1 leaves
   them so in a statement it does not analyse, MERGE, and reports no
   parameter for them; PostgreSQL then reads `@amount` as the absolute value
   of the column `amount`, silently. `@>`, `<@`, `@@` and `@-x` are operators. *[2]:
   held to libpg_query's own scanner by `tests/py/scanner.py` (see Proof).
   Where libpg_query and PostgreSQL disagree, sqlc's numbering follows
   libpg_query: it does not continue an `E` string after a `--` comment and
   a newline (`E'a' -- c` `\n` `'\'b'`), which PostgreSQL does.*
2. **Colons.** SQLAlchemy reads `(?<![:\w\\]):(\w+)(?![:\w])` as a bind, and
   when it renders the statement turns `\\(:\w*)(?![:\w])` back into
   the colon and word. Every literal `:` from `query.text` MUST be written
   `\:` (rendered `\\:` in the Python source): `$1::uuid[]` becomes
   `:ids\:\:uuid[]`, `x::numeric` becomes `x\:\:numeric`, and
   `'{"vip":true}'` becomes `'{"vip"\:true}'`. An escaped colon is never a
   bind, and is always turned back: the word after it ends at no `:`, as
   every other colon is escaped too. So sqlc's text comes back byte for byte,
   whatever a word character is to the Python running, whose Unicode
   differs by version. *[3]: probed; minimal escaping is possible but not
   simpler, as `:ids::uuid[]` silently binds nothing, `:x\:\:text::int`
   keeps its backslash, and Python 3.10 binds `:x` in `'\u0870:x'` where
   3.15 does not.*

   A placeholder `text()` would not bind as one MUST be an error: directly
   after `:`, `\` or a word character (as in `[$1:$2]`, `$1$2` or `0x1F$1`),
   or directly before a word character (as in `$1a`, which PostgreSQL scans
   as `$1 a`, an alias, and `text()` as the bind `:ida`). A word character
   here is an ASCII letter, digit or `_`, or any character outside ASCII,
   which some supported Python may read as a letter; PostgreSQL's lexer
   takes such a character into a word too, so no placeholder it reads is
   refused for it.
3. **Invariant.** SQLAlchemy's bind expression MUST find exactly the
   parameter names in the emitted text. Rendering each as its placeholder and
   then unescaping with SQLAlchemy's own expression, as the compiler does, MUST
   give `query.text` byte for byte. `cargo test` checks this for every query
   of every golden case and corpus request (`tests/output/support`).
4. **Typed statements**, only where a driver needs them, and nothing else gets
   a type: *[3]*
   - Each `json`/`jsonb` parameter gets
     `.bindparams(sqlalchemy.bindparam("<name>", type_=postgresql.JSONB(none_as_null=True)))`,
     with `postgresql.JSON` for `json`. Both drivers reject a `dict`. Without
     `none_as_null`, `None` would be stored as JSON `null`, not SQL NULL.
   - A result with an enum-array column gets `.columns(...)` with every
     result column positionally, in order: `sqlalchemy.column("<field>")`, and
     `sqlalchemy.column("<field>", postgresql.ARRAY(sqlalchemy.Enum(*models.X)))`
     for each enum array. psycopg returns `enum[]` as the raw string
     `'{card,direct-debit}'`, and asyncpg returns a list; this type makes both
     a list. `from_row` still does the coercion (§4, rule 4).
   - SQLAlchemy matches a positional list by position and ignores its names,
     which are the Python fields'. Typing by name (`.columns(<name>=...)`)
     would silently miss a column PostgreSQL names differently from sqlc
     (`coalesce(accepted_methods, '{}')` is `coalesce` to PostgreSQL), would
     type every column of a repeated name, and cannot compile the empty name
     of an unnamed column. Planted bug "enum arrays typed by name".
   - `.bindparams(...)` comes before `.columns(...)`.

### Functions

1. The signature MUST be
   `def <name>(conn: <connection>, *, <param>: <type>, ...) -> <result>`:
   - `conn` is positional, annotated as the backend's connection:

     | Backend | `async: false` | `async: true` |
     |---|---|---|
     | `sqlalchemy` | `sqlalchemy.Connection` | `AsyncConnection` |
     | `psycopg` | `psycopg.Connection[Any]` | `psycopg.AsyncConnection[Any]` |
     | `sqlite3` | `sqlite3.Connection` | `aiosqlite.Connection` |

   - every SQL parameter follows it keyword-only, in sqlc's parameter order,
     with no defaults;
   - with no parameters there is no `*`;
   - parameters are never grouped into a class (only `:copyfrom` rows are a
     `<Query>Params`, rule 6), and there is no parameter limit.

   *[D]: keyword-only parameters cannot be silently swapped. A forgotten
   nullable parameter is a type error, never a NULL written to an invoice.*
2. The body MUST execute the constant exactly once, and shape the result as
   below. The caller owns the connection and its transaction: nothing is
   committed. *[D]* A coroutine differs from the function only in
   `async def`, its connection, and `await` on each execution and fetch.
   - SQLAlchemy: `conn.execute(<constant>, {"<name>": <name>, ...})`,
     the dict omitted when there are no parameters;
   - psycopg: `psycopg.RawCursor(conn, row_factory=tuple_row)`
     `.execute(<constant>, (<p1>, <p2>, ...))`, each parameter in its
     placeholder's place, and a JSON one as `None if p is None else Jsonb(p)`
     (`Json` for `json`). A raw cursor takes `$N`; the row factory makes rows
     tuples whatever the connection's is; psycopg cannot tell a JSON document
     from any other `dict` or `list`, and `None` stays SQL NULL. *[3]*
   - `sqlite3`: `conn.execute(<constant>, (<p1>, <p2>, ...))`.
3. Results, by command. *[2] cmd*

   | cmd | Returns | SQLAlchemy | psycopg, `sqlite3` |
   |---|---|---|---|
   | `:one` | `X` | `X.from_row(….one())` | `match cur.fetchmany(2):` with `case [row]: return X.from_row(row)`, `case []: raise NoRowError`, `case _: raise MultipleRowsError` |
   | `:many` | `list[X]` | `[X.from_row(row) for row in …]` | `[X.from_row(row) for row in cur.fetchall()]` |
   | `:exec` | `None` | `….execute(…)` | `….execute(…)` |
   | `:execrows` | `int` | `….rowcount` | `….rowcount` |
   | `:execresult` | the result | `sqlalchemy.CursorResult[Any]` | the cursor: `psycopg.RawCursor[tuple[Any, ...]]` (`AsyncRawCursor`), `sqlite3.Cursor` (`aiosqlite.Cursor`) |
   | `:copyfrom` | `None` | rule 6 | rule 6 |

   - `:one` raises without exactly one row, as sqlc's Go returns
     `ErrNoRows`, so a created invoice is an `Invoice`, never an
     `Invoice | None`; a lookup where absence is normal catches it. On
     SQLAlchemy that is `one()` (or `scalar_one()`): no row raises
     `sqlalchemy.exc.NoResultFound`, a second `MultipleResultsFound`. A
     driver has no such errors, so the package defines them in
     `__init__.py`, as `class NoRowError(LookupError)` and
     `class MultipleRowsError(LookupError)`. Go silently takes the first of
     several rows; this divergence is deliberate: a lookup that is not unique
     must not pick an invoice. Reading with `.first()` or `.scalar()` instead
     is a type error, since either may be `None` (planted bugs ":one takes
     the first row" and ":one takes the first value").
   - `:many` is always eager. *[D]: a lazy generator would let an
     `UPDATE … RETURNING` never run. Planted bug ":many returns a lazy
     generator".*
   - On SQLAlchemy, `:execrows` and `:execresult` on a statement holding
     `MERGE INTO` are an error. *[3]: SQLAlchemy reads asyncpg's row count
     off the command tag, with an expression that knows no `MERGE n`, so it
     is `-1` there and the real count on psycopg; a count that is wrong on
     one driver is worse than none (rule 6).*
4. **What `X` is.**
   - **A single non-embed column** is returned bare: `T`, `list[T]`, through
     `.scalar_one()` or `.scalars()` on SQLAlchemy, or as `row[0]` on a driver,
     so a nullable column's `None` is its
     NULL and nothing else. An enum is converted with the same expression
     `from_row` would use. *[4]: Go returns the bare value too.*
   - **A table's model** is reused when the result has at least two columns,
     and they are exactly that table's columns: the same table, names, order,
     types and nullability. *[4] (sqlc-gen-go's rule)*
   - **Anything else** is a `<Query>Row` defined in the query module.
5. **Embeds.** `sqlc.embed(t)` arrives as one column with `embed_table` and no
   type. *[2]* It MUST become a field typed as `t`'s model, built by
   `models.M.from_row(row[a:b])` over `t`'s columns in catalog order. *[4]*
6. **`:copyfrom`.** The function MUST be
   `def f(conn, rows: Iterable[<Query>Params]) -> None`, running a single
   executemany of one row of parameters per row, its fields written out. On
   SQLAlchemy those are dicts, and an empty list runs nothing, as SQLAlchemy
   raises on one; a driver's `executemany` runs none for it itself.
   - asyncpg reports `rowcount == -1` for executemany, so no count is returned;
     a count that is wrong on one driver is worse than none.
   - sqlc rejects `ON CONFLICT`, `RETURNING` and non-parameter values in
     `:copyfrom`. *[2], [3]*
7. **`sqlc.narg`** is a nullable parameter: `T | None`, still required. A
   parameter used several times arrives once. *[2]*
8. **`= ANY(@ids::type[])`** is how to pass a list. The parameter is
   `list[T]`, and an empty list matches nothing (tested). Without the cast,
   sqlc types the parameter as the element (`WHERE mood = ANY($1)` takes a
   `models.Mood`), and PostgreSQL rejects the call.

## 8. Errors

Unsupported input MUST fail generation, never warn: sqlc shows stderr only on
failure. *[1]* A message names where the problem is, then what is wrong, then
what to do instead:

```text
<file>: query "<Name>": parameter $<N> ("<name>") has type "<type>", which has no verified Python mapping
<file>: query "<Name>": column "<col>" has a type sqlc could not infer; add a cast, as coalesce(<expr>, <default>)::<type> if it can be NULL, since sqlc reports every cast NOT NULL
<file>: query "<Name>": parameter $<N> ("<name>") has a type sqlc could not infer; add a cast, as @<name>::<type>, or sqlc.narg('<name>')::<type> if it can be NULL
<file>: query "<Name>": :batchexec is pgx-only; use :copyfrom for bulk inserts, or :exec with = ANY(@ids::type[])
<file>: query "<Name>": sqlc did not rewrite @amount into a placeholder, as it does not in a statement it does not analyse, such as MERGE; write it as INSERT ... ON CONFLICT, or UPDATE ... FROM
table "<table>": column "<col>" is an array, but sqlc reported no array depth for it
table "<table>": column "<col>" is an array of "citext", which psycopg returns as text, not a list
enum class `<Class>`: psycopg returns an array of this enum as its text, in which PostgreSQL quotes the label "<label>"; rename the label, or use the sqlalchemy backend
the psycopg backend does not run sqlite
engine "mysql" is not supported yet; only postgresql and sqlite are
```

Where is a query (`<file>: query "<Name>": `), a query file (`<file>: `), a
table (`table "<table>": `), an enum (`enum "<enum>": `), or nothing for the
catalog as a whole (two classes of one name, an engine). Every error, and
every rule above that makes one, is specified with its message in the unit
specs (`src/*_spec.rs`); `docs/compat.md` lists the ones the sqlc corpus
meets.

## Known limitations

These are documented, not detected. Each follows from never re-inferring what
sqlc reports *[2]*.

- **Embeds on the nullable side of an outer join.** sqlc marks every embed
  column nullable and cannot tell inner joins from outer ones. Like Go, the
  embed is typed as the model, so an unmatched outer row would build a model
  full of `None`. Do not embed the optional side of an outer join; select its
  columns instead.
- **Computed columns are NOT NULL to sqlc**, including every cast, even of
  a nullable value: `max(created)::timestamptz` on a nullable column is
  annotated `dt.datetime`, and an empty table returns `None`. Generation
  fails for the types sqlc guesses (§5, rule 2), but not for this. Coalesce
  anything that can be NULL: `coalesce(sum(x), 0)::numeric(12, 2)`, as the
  fixture's `GetInvoiceTotals` does.
- **Subqueries on the nullable side** are NOT NULL to sqlc: a scalar
  subquery (`(SELECT note FROM b WHERE b.a_id = a.id LIMIT 1) AS note`), a
  subquery joined with `LEFT JOIN (SELECT ...) s`, and `LEFT JOIN LATERAL`
  all annotate `note` as `str`, and return `None` where nothing matched.
  Join the table itself instead: in `LEFT JOIN b ON b.a_id = a.id`, `b.note`
  is `str | None`. Where a default will do, coalesce and cast the value
  instead.
- **`NULLIF`** is reported as a NOT NULL `bool`, whatever its arguments, and
  that is indistinguishable from a real `bool` column. Cast it, coalesced:
  `coalesce(nullif(discount, 0), 0)::numeric(12, 2)`.
- **Operators and functions with a parameter** take the operand's type as
  sqlc guesses it: `d + $1` on a `date` column types the parameter
  `dt.date`, and PostgreSQL rejects the call (`operator is not unique: date +
  unknown`). A comparison with a function's result takes the type of the
  function's first column: `extract(year from issued) = @yr` and
  `to_char(issued, 'YYYY') = @yr` type `yr` as `dt.date`. A parameter passed
  to a function takes the guessed overload's argument type, which §5, rule 2
  only catches when it is spelled with SQL's standard name: `substr(@s, 2)`
  is `bytes`, since `substr(bytea, int)` is listed first. Cast the
  parameter: `d + @days::int`, `abs(@amount::numeric)`.
- **Function results through a view, CTE or subquery** that §5, rule 2
  cannot catch, because the guessed overload's type has the name a
  declaration would give it: `string_agg`, `substr`, and `btrim`, `ltrim`
  and `rtrim` of two arguments are `bytes` (the `bytea` overloads are listed
  first), and `age(t)` is an `int` (`age(xid)`). Cast every computed column
  inside a view, CTE or subquery, as in a query.
- **A parameter compared with a cast column** takes the column's type, not
  the cast's: `issued_at::date = @day` types `day` as `dt.datetime`, and the
  drivers then disagree (psycopg compares the instant, asyncpg the date).
  Cast the parameter too: `issued_at::date = @day::date`.
- **Row comparisons** give every parameter the first column's type:
  `(issued_at, id) < (@after_at, @after_id)` types `after_id` as a
  `dt.datetime`. Cast each one: `(@after_at::timestamptz, @after_id::uuid)`.
- **`CASE`** takes its `ELSE` branch's type and is NOT NULL to sqlc, whatever
  the other branches return: `CASE WHEN paid THEN total ELSE 0::int END` is
  an `int` that comes back as a `Decimal`. Cast the whole expression,
  coalesced: `coalesce(CASE ... END, 0)::numeric(12, 2)`.
- **Parameters of an `ARRAY[...]` constructor** take the array's type:
  `ARRAY[$1, $2]::int[]` types both `list[int]`, which PostgreSQL rejects,
  while the `int` it accepts fails the type checker. Cast each element:
  `ARRAY[@a::int, @b::int]`.
- **NULL array elements.** `{a,NULL}` in a `text[]` column comes back as
  `['a', None]` against `list[str]`. Use a `CHECK (array_position(col, NULL) IS
  NULL)` constraint where it matters.
- **Array dimensions are not enforced.** PostgreSQL accepts `'{1,2}'` in an
  `int[][]` column, read back as `[1, 2]` against `list[list[int]]`, and
  `'{{1,2},{3,4}}'` in an `int[]` one. Add `CHECK (array_ndims(col) = N)`
  where it matters.
- **A coalesce whose first argument is a NOT NULL column** looks exactly
  like that column, so §5, rule 2 cannot catch it, and takes its type and
  NOT NULL: `coalesce(qty, 1.5)` on a NOT NULL `int` column is annotated
  `int` and returns `Decimal`, and `coalesce(b.x, c.y)` with `b` and `c` on
  the nullable side of outer joins is annotated `str` and returns `None`
  where neither matched. End every coalesce with a default of the type you
  want, and cast it: `coalesce(b.x, c.y, '')::text`.
- **`UNION`, `INTERSECT` and `EXCEPT`** take the first branch's type and
  nullability: `SELECT name FROM a UNION ALL SELECT NULL` is `list[str]` and
  returns `None`, and an `int` branch then a `numeric` one is annotated `int`
  and returns `Decimal`. A view or CTE over such a query inherits it. Coalesce
  and cast the column in every branch.
- **Parenthesised joins.** In `a LEFT JOIN (b JOIN c ON ...) ON ...`, sqlc
  reports `b`'s and `c`'s columns NOT NULL, and they are `None` for an
  unmatched row. Write a chain instead: `a LEFT JOIN b ON ... LEFT JOIN c ON
  ...`.
- **`GROUP BY ROLLUP`, `CUBE` and `GROUPING SETS`** leave the grouped columns
  NOT NULL, and their total rows hold `None`. Coalesce and cast the grouped
  columns.
- **`interval` loses months.** Both drivers return a `dt.timedelta`, which has
  no months: `'1 mon'` comes back as 30 days, and binds back as `'30 days'`
  (`docs/typemap.md`). Where a billing period is a month, store it as a
  number of months (`int`), or as dates, never as an `interval`.
- **The drivers disagree on time zones.** A naive `datetime` passed for
  `timestamptz` is read in the session's `TimeZone` by psycopg, and in the
  process's local time by asyncpg: pass aware datetimes. An aware one passed
  for `timestamp` (without time zone) is converted to the session's wall
  time by psycopg (23:30Z is stored as 00:30 the next day in
  Europe/Amsterdam), and raises in asyncpg. A `timestamptz` comes back in the
  session's `TimeZone` on psycopg and in UTC on asyncpg, so `.date()` of one
  near midnight names a different day per driver: convert it first,
  `created_at.astimezone(tz).date()`. A stored `'infinity'` raises in
  psycopg and is the naive `datetime.max` on asyncpg, which raises when
  compared with an aware one: keep infinities out of `timestamptz` columns.
- **A `datetime` is a `date`** to every type checker, since it subclasses it,
  so a `dt.datetime` passed for a `date` parameter type-checks. psycopg then
  sends a `timestamptz`, which PostgreSQL turns into a date in the session's
  `TimeZone` (23:30Z on 31 January is 1 February in Europe/Amsterdam), and
  asyncpg drops the time (31 January); `WHERE bill_day = @day` matches on one
  driver and not the other. Pass a `dt.date`, from `.date()` after
  converting.
- **JSON `null` versus SQL NULL.** `None` always writes SQL NULL, and a stored
  JSON `null` reads back as `None`.
- **A `bool` is an `int`** to every type checker, as it subclasses it, so
  `True` type-checks for any `int` parameter. asyncpg binds it as `1` and
  writes it; psycopg raises (`column is of type bigint but expression is of
  type boolean`). `usage.py` pins it.
- **A JSON parameter is an `object`**, so it type-checks with any value, and
  the drivers serialise it with `json.dumps` at runtime: a `Decimal`,
  `UUID` or `datetime` inside it raises `TypeError` on every driver, so
  convert amounts to strings first (`str(amount)`), never to `float`. `None`
  is SQL NULL even where the parameter is NOT NULL, and a `str` is stored as
  a JSON string, not parsed: pass `json.loads(text)` for JSON text. A recursive JSON type would reject only the first, and
  would refuse a `dict[str, str]`, since `dict` is invariant. `usage.py` pins
  the `Decimal`.
- **Records hash, but their lists do not.** A frozen dataclass gets a
  `__hash__`, so every type checker accepts a record in a `set` or as a
  `dict` key, and one with a list or JSON field raises `TypeError` there.
  Its list can also be changed in place (`row.tags.append(...)`), frozen or
  not. Declaring such records unhashable takes `__hash__ = None`, which both
  checkers reject without a `# type: ignore`; tuples for results would not
  cover JSON, and would differ from the lists parameters take. Key by a field instead (`{r.id: r for r in rows}`), and
  copy a list before changing it. `usage.py` pins the hash.

## Proof

This section is the one description of how the output is proven; the
commands are `cargo xtask help`.

`cargo test` holds every golden case and every corpus output to the
invariants any correct output meets, listed in `tests/output/corpus.rs` and
each specified by a planted bug in `tests/output/invariants.rs`. They are
what no type checker or runtime probe can see, such as a NOT NULL column
annotated `X | None`, two parameters of one type bound to each other's
names, a field named after another column, a dropped docstring, or a
`# type: ignore`. `cargo xtask check` then holds every distinct output, golden
and corpus, to the [static gate](#lint-contract) (`tests/py/gate.py`), and
runs the scanner proof:

- **the scanner proof** (`tests/py/scanner.py`) holds SQLAlchemy's
  rewriting (§6, "On SQLAlchemy", rules 1 and 2) to PostgreSQL's own
  scanner. Hypothesis draws a few
  thousand texts, the same on every run, from a grammar of what PostgreSQL
  scans specially (standard, `E`, `U&` and bit strings, with `''`,
  backslashes and continuations; dollar quotes and tags; nested and line
  comments ending at `\n`, `\r` or the end; quoted identifiers; casts and
  colons; identifiers holding `$`; non-ASCII; `@` and `sqlc.arg`),
  placeholders glued to all of them. For each that pglast (libpg_query, the
  scanner sqlc parses with) scans, the plugin's rewriting
  (`examples/sql_text.rs`) must bind exactly the placeholders it reports, at
  their positions, so that SQLAlchemy's `text()` compiles back to the input
  byte for byte, as SQLAlchemy renders it and as its asyncpg dialect sends
  it, or refuse it for one of the reasons rules 2 and 3 name, read off
  pglast's tokens. This is what holds the PostgreSQL lexer to libpg_query: a placeholder
  taken for text, or text for a placeholder, still round-trips in `cargo
  test`. It needs no database, and runs on the oldest Python only: escaping
  every colon, and refusing a placeholder beside any non-ASCII character,
  makes the rewriting the same whatever a Python takes for a word character.

Then `cargo xtask verify [--mutants]` (`tests/py/verify.py`) runs these
layers:

- **the static gate** (`tests/py/gate.py`, the [Lint contract](#lint-contract)),
  over the golden cases and over `usage.py`, on every Python in `PYTHONS`.
  `usage.py` pins the types application code sees and lists the mistakes that
  must stay type errors: positional arguments, a missing nullable argument, a
  `str` for an enum, a `float` for money, a tuple for an array, mutating a row,
  and building a row by position. It also pins the known holes no
  annotation can close, so that they stay visible: a `datetime` for a
  `date`, a `bool` for an `int`, a `Decimal` inside JSON, and hashing a
  record that holds a list.
- **pytest** (`tests/py/suite/`):
  - `test_runtime.py` runs one invoicing scenario through every function
    against the newest PostgreSQL (`NEWEST` in `tests/py/postgres.py`, in
    Docker, or `SQLC_TEST_DATABASE_URL`): `invoicing_sqlalchemy` on psycopg,
    `invoicing_sqlalchemy_async` on asyncpg and psycopg async, and
    `invoicing_psycopg` and `invoicing_psycopg_async`. Every argument and result is checked against
    its annotation exactly, `:one` must raise the backend's errors, and any
    function never called fails the run;
  - `test_sqlite.py` runs a ledger scenario through every function of
    `ledger_sqlite3` on `sqlite3`, `ledger_sqlite3_async` on `aiosqlite`, and
    `ledger_sqlalchemy` and `ledger_sqlalchemy_async` on SQLAlchemy's
    `sqlite` and `sqlite+aiosqlite`, in process;
  - `test_contract.py` checks that the copies of SQLAlchemy's expressions
    `cargo test` uses are SQLAlchemy's.

  Every pytest run fails if it skips a test or collects an empty
  parametrization, so a layer cannot pass by running nothing.
- **the type-truth probe** (`tests/py/typemap.py`) selects every type in the
  map at its edges (NULL, extremes, NaN and infinities, unicode, empty and
  two-dimensional arrays) through all three drivers, and fails on a value
  outside the annotation the generator writes in
  `tests/cases/pgtypes_sqlalchemy*`, or JSON that is not the decoded document.
  What raises, or does not bind back to the value it read, is recorded in
  `docs/typemap.md`.
- **the runtime sweep** (`tests/py/autoprop.py`) applies the schema of every
  PostgreSQL golden case and corpus request generated on SQLAlchemy to a
  fresh database, seeds every table, and calls every function and coroutine
  with arguments Hypothesis draws,
  checking each argument and result against its annotation. It fails on a
  type mismatch, a crash, a bind error, or a schema PostgreSQL rejects,
  which would leave a package proven by nothing; a call the database refuses (a
  constraint, a value, SQL PostgreSQL cannot plan) is inconclusive. A
  function counts as exercised once a call returned rows (or, for a command
  that returns none, ran), and the share exercised must stay above a
  committed floor. That share is all this layer says about a well-typed bug
  that makes PostgreSQL refuse every value bound for some parameter: its
  calls become inconclusive, and a few such functions fit within the
  floor's margin. Which functions are exercised varies between runs, so a
  per-function list cannot replace it. Each call of a sync `:one`,
  `:many` and `:execrows` is also compared with sqlc's own text run directly
  with the same arguments, through psycopg's `RawCursor`, which takes `$N` as
  written: the rows, as a multiset, or the row count must be the same. That
  holds the SQL rewriting, the binding and the reading of each result to a
  reference sharing none of the generator's code, for every corpus query; a
  statement whose two direct runs differ (a sequence, `random()`) is not
  compared, and the sweep fails if nothing was. Where sqlc
  misreports a schema (the known limitations above among them), the failure
  is listed in `tests/py/known-failures.tsv`.
  What it called, with the corpus ledger, is `docs/compat.md`: for each sqlc
  feature, per engine and backend, whether at least one query using it ran
  at runtime (on PostgreSQL) or all only generated, and how many of them are
  a clean error.
- **newer Pythons**: pytest, the type-truth probe and the runtime sweep run
  again on every newer Python in `PYTHONS`, which installs SQLAlchemy 2.1
  where 3.10 has 2.0. The documents record the oldest.

With `--mutants`, plausible generator bugs (`MUTANTS` in `verify.py`) are
planted one at a time, and each must be caught by the layer named for it,
which alone runs on it: the gate, `test_runtime.py` (with `-x`), the
type-truth probe, or the runtime sweep over that golden case, whose
comparison with sqlc's SQL run directly must catch two columns of one type
swapped. It must fail saying what the mutant names: a part of that layer's
failure, such as the field `deep.check` found wrong or the rule a checker
broke. So a mutant cannot count as caught because something unrelated
failed, even in the one test that holds every runtime assertion. The
mutants are bugs only these layers can see; what `cargo test` holds every
output to is specified by its own planted bugs, and what `usage.py` holds
the types to, by its `# type: ignore` lines, which the gate fails on once
they are unused. With `--check`, as CI runs
it, a document that would change fails the run instead of being written.
`cargo xtask bless` also runs `verify` before it accepts a change to
`tests/cases/pgtypes_sqlalchemy` or the invoicing and ledger cases, since a wrong type that
is still well typed passes the static gate, and so updates the documents with
it.
